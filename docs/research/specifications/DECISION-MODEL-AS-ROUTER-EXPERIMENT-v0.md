# Decision Model as Router — Experiment v0\n\nStatus: DESIGN / OPEN  \nFrozen Core: unchanged  \nExperiment role: research only; no production routing authority\n\n## 1. Hypothesis\nA lightweight decision model can act as a first-stage router that reduces downstream LLM/specialist workload while preserving acceptable task-level correctness only when its routing decisions are independently evaluated and fail closed on uncertainty.\n\nThe experiment does not assume that a decision model is truthful, safe, or sufficient as a sole control.\n\n## 2. Research question\nCompared with sending every case directly to the reference evaluator, does a decision-model router:\n1. reduce downstream evaluation cost/latency;\n2. preserve correctness on cases it routes to an automatic path;\n3. identify uncertain or high-risk cases for escalation;\n4. remain robust under adversarial or distribution-shifted inputs?\n\n## 3. Formal hypothesis\nLet M = decision model; R = routing policy using M; E = reference evaluator / specialist; y = task ground truth; c = case; a_R(c) = route selected by R.\n\nPrimary hypothesis H1:\n`R(M(c))` can reduce E invocation rate while keeping the error rate of the complete routed system within a predeclared acceptance bound.\n\nNull hypothesis H0:\n`R(M(c))` does not provide a statistically and operationally meaningful reduction in downstream workload at the required correctness/safety bound.\n\nNo causal conclusion may be drawn from aggregate agreement alone.\n\n## 4. Experimental arms\nA. Direct baseline\n- Every case goes to E.\n- Establishes reference correctness, latency, and cost.\n\nB. Router\n- M evaluates every case.\n- Low-risk / high-confidence cases follow the predefined automatic route.\n- Uncertain or high-risk cases escalate to E.\n\nC. Router + calibration\n- Same as B, with calibration performed only on a declared calibration split.\n- Calibration data must be disjoint from evaluation data.\n\nD. Adversarial / shift evaluation\n- Same routing policy as B/C.\n- Uses predefined adversarial and distribution-shifted cases.\n- No threshold tuning on the evaluation set.\n\n## 5. Primary measurements\nRecord per case:\n- case_id\n- dataset_split\n- model_id\n- model_version\n- prompt_or_policy_hash\n- routing_policy_id\n- raw_model_output\n- normalized_route\n- confidence, if supplied\n- calibration_version, if applicable\n- reference_decision\n- final_system_decision\n- escalated_to_reference\n- latency_ms\n- token/cost counters when available\n- evidence/provenance identifiers\n\nPrimary metrics:\n1. downstream_escalation_rate\n2. end_to_end_error_rate\n3. automatic_route_error_rate\n4. false_negative_rate for safety-critical cases\n5. false_positive_rate where applicable\n6. p50/p95 latency\n7. estimated cost per case\n8. coverage of automatic decisions\n\nSecondary metrics:\n- calibration error / reliability\n- abstention quality\n- performance by task class\n- performance by difficulty\n- performance by adversarial category\n- performance by distribution-shift category\n- disagreement rate M vs E\n\n## 6. Acceptance contract\nThresholds MUST be declared before evaluation.\n\nMinimum required contract:\n- safety-critical false-negative bound: predefined per task;\n- end-to-end error bound: predefined relative to direct baseline;\n- minimum workload reduction: predefined;\n- maximum latency regression: predefined;\n- calibration acceptance bound: predefined when confidence is used.\n\nIf any required bound is not defined before the run: `STATUS = INCONCLUSIVE`.\nIf required evidence is missing: `STATUS = INCONCLUSIVE`.\nNo threshold may be changed after observing evaluation results without starting a new experiment version.\n\n## 7. Statistical design\nUse paired evaluation whenever the same cases can be evaluated across arms.\n\nReport:\n- N total;\n- N by split/category;\n- paired differences;\n- confidence intervals;\n- predefined statistical test and alpha;\n- effect size.\n\nA statistically significant difference does not by itself establish practical usefulness.\nIf the experiment is underpowered for a declared claim: `STATUS = INCONCLUSIVE`.\n\n## 8. Adversarial protocol\nAdversarial cases must be generated or selected before the evaluation run and versioned.\n\nRequired categories should include, where applicable:\n- plausible-but-malicious instructions/code;\n- prompt injection;\n- misleading semantic framing;\n- benign-looking payload with unsafe intent;\n- distribution shift;\n- ambiguous cases.\n\nThe router must not be evaluated only on cases resembling its calibration set.\n\n## 9. JAMP epistemic contract\nThe decision model is an observation source.\n\nIts output is: `OBSERVED`.\n\nIt is not, by itself:\n- evidence;\n- authorization;\n- truth;\n- safety clearance;\n- merge authority;\n- state-transition authority.\n\nThe router may select an investigation path, but JAMP evidence gates determine whether a conclusion is supportable.\n\nPipeline:\n`decision model → routing observation → reference/escalation → evidence collection → JAMP verification → decision`\n\nConflicts between M and E are preserved, not silently averaged.\n\n## 10. Fail-closed rules\nThe experiment MUST return `INCONCLUSIVE` when:\n- model version is not pinned;\n- routing policy hash is missing;\n- evaluation split is not identifiable;\n- calibration/evaluation separation cannot be verified;\n- reference labels are unavailable where required;\n- required adversarial set is missing;\n- required metrics cannot be computed;\n- provenance is incomplete;\n- acceptance thresholds are absent or changed post hoc.\n\nNo missing-data path may produce a synthetic PASS.\n\n## 11. Provenance\nEvery result artifact must bind:\n- experiment_id;\n- experiment_version;\n- commit SHA;\n- model_id;\n- model_version;\n- routing_policy_id/hash;\n- dataset/split identifier;\n- calibration identifier, if used;\n- seed, if stochastic;\n- environment/runtime metadata;\n- timestamp;\n- result artifact hash.\n\nTarget artifact:\n`artifacts/research/decision_model_router_v0.json`\n\nSuggested experiment identifier:\n`EXP-ROUTER-DECISION-MODEL-V0`\n\n## 12. Decision states\nAllowed terminal states:\n- `VERIFIED` — all required evidence and acceptance criteria are satisfied;\n- `CONTRADICTED` — predefined hypothesis is contradicted by the experiment;\n- `INCONCLUSIVE` — evidence is insufficient or acceptance contract cannot be evaluated.\n\nDo not use `PASS`, `FAIL`, or `GREEN` as the scientific result.\n\n## 13. Frozen Core\nThis experiment MUST NOT modify:\n`src/jamp/run.py`\n\nLocked blob:\n`0fee0e1c5c1a1548361965ac51eacdeba62bfe8a`\n\nExperiment implementation must remain outside Frozen Core.\n\n## 14. Implementation sequence\nPhase 0 — contract\n- freeze experiment schema;\n- freeze thresholds;\n- freeze dataset splits;\n- freeze routing policy.\n\nPhase 1 — baseline\n- run direct evaluator;\n- establish reference measurements.\n\nPhase 2 — router\n- run decision-model routing;\n- collect per-case provenance.\n\nPhase 3 — calibration\n- run only if a separate calibration split exists.\n\nPhase 4 — adversarial/shift\n- evaluate frozen router on held-out adversarial/shift sets.\n\nPhase 5 — analysis\n- compute paired metrics and statistical tests;\n- classify each criterion as `VERIFIED`, `CONTRADICTED`, or `INCONCLUSIVE`.\n\nPhase 6 — replay\n- reproduce the result from the pinned commit/model/policy/dataset identity.\n\n## 15. Non-claims\nThis experiment does not establish that:\n- one decision model is universally better than another;\n- a decision model can safely replace human support;\n- a decision model can replace a specialist/LLM in all tasks;\n- benchmark performance transfers automatically to production;\n- model confidence is calibrated merely because it is numerically expressed.\n\nThose are separate hypotheses requiring separate evidence.
