1. Purpose

EVERYNODE — проект распределённой инфраструктуры хранения данных, использующей физические ресурсы устройств участников сети.

Цель проекта — создать децентрализованную систему, позволяющую распределять зашифрованные фрагменты пользовательских данных между независимыми узлами, контролировать их сохранность и восстанавливать исходные данные при потере части узлов.

EVERYNODE рассматривается как самостоятельная Infrastructure Layer.

Независимая проверка утверждений о работе инфраструктуры может выполняться JAMP — отдельной системой Trust Layer.

Этот документ определяет архитектурные принципы и технические границы EVERYNODE.

Он не является доказательством существующей реализации, производительности или готовности сети.

2. Architectural Principles

Архитектура строится на следующих принципах.

2.1. Decentralization

Система не должна зависеть от единственного центрального узла хранения.

Потеря одного или нескольких участников не должна автоматически приводить к потере исходных данных.

2.2. Client-Side Encryption

Данные шифруются на стороне клиента до передачи внешним узлам хранения.

Узлы хранения получают зашифрованные данные и не должны иметь доступа к исходному содержимому.

2.3. Data Integrity

Каждый объект хранения должен иметь проверяемую идентичность.

Изменение, повреждение или подмена фрагмента должны обнаруживаться посредством криптографических механизмов контроля целостности.

2.4. Fault Tolerance

Система должна сохранять возможность восстановления данных при отказе части узлов.

Устойчивость определяется выбранной схемой избыточности, распределением фрагментов и фактической доступностью узлов.

2.5. Independent Verification

EVERYNODE не является единственным источником подтверждения собственной надёжности.

Система должна предоставлять проверяемые свидетельства, которые могут независимо анализироваться внешним Trust Layer.

2.6. Modular Architecture

Хранение, сетевое обнаружение, распределение, проверка доступности и дополнительные ресурсы должны быть разделены на независимые компоненты.

Добавление новых типов ресурсов не должно требовать переписывания базового протокола хранения.

2.7. Cryptographic Accountability

Каждое существенное решение системы должно сопровождаться воспроизводимой цепочкой доказательств.

Неопределённость трактуется как отказ в положительном вердикте (Fail-Closed).

Отсутствие доказательств не эквивалентно доказательству отсутствия проблемы.

3. System Architecture

Предлагаемая архитектура состоит из следующих логических компонентов.

Component | Responsibility
Client | Подготовка и восстановление пользовательских данных
Encryption Engine | Клиентское шифрование и управление криптографическими операциями
Chunking Engine | Разбиение данных на блоки
Erasure Coding Engine | Создание избыточных фрагментов
Node Agent | Выполнение операций хранения на устройстве
Placement Engine | Выбор узлов для размещения фрагментов
Network Discovery | Обнаружение участников сети
DHT Layer | Распределённое обнаружение записей и узлов
Integrity Engine | Контроль целостности объектов
Recovery Engine | Восстановление исходных данных
Evidence Interface | Формирование технических свидетельств для внешней проверки

Это логическое разделение. Оно не предписывает конкретный язык программирования или физическое количество процессов.

4. Node Classes

Узлы различаются по техническим возможностям и ожидаемому режиму работы.

4.1. Mobile Node

Устройство: смартфон; планшет; другое мобильное устройство.

Возможности: ограниченное дисковое пространство; переменное качество соединения; ограниченная автономная работа; зависимость фоновых задач от операционной системы; ограниченная вычислительная производительность.

Ограничения: мобильный узел не должен считаться постоянно доступным. Система должна учитывать ограничения фоновых процессов; энергопотребление; состояние батареи; доступность сети; свободное пространство; ограничения операционной системы.

Мобильные устройства не должны получать обязательства по непрерывному хранению без подтверждённой технической возможности.

4.2. Desktop Node

Устройство: персональный компьютер; рабочая станция; ноутбук.

Возможности: более значительный объём хранения; более высокая вычислительная производительность; возможность длительной работы; подключение к локальным и внешним сетям.

Ограничения: выключение пользователем; переход в спящий режим; изменение сетевого подключения; изменение доступного дискового пространства.

4.3. Always-on Node

Устройство: домашний сервер; мини-ПК; выделенный сервер; постоянно работающая система хранения.

Предполагаемые характеристики: длительное время работы; стабильное питание; предсказуемая доступность; возможность выделения ресурсов под хранение.

Даже Always-on Node не считается гарантированно доступным.

Фактическая доступность должна подтверждаться наблюдениями и проверяемыми свидетельствами.

4.4. Node Capability Profile

Каждый узел должен иметь технический профиль: Node ID; тип устройства; доступная ёмкость; выделенная ёмкость; свободное пространство; доступная пропускная способность; сетевые характеристики; версия программного обеспечения; время последнего контакта; текущий статус.

Node ID должен быть криптографически связан с идентичностью узла.

Сам по себе Node ID не доказывает существование независимого физического устройства.

5. Data Architecture

5.1. Data Lifecycle

Предлагаемый жизненный цикл объекта:

1. Пользователь выбирает файл.
2. Клиент вычисляет идентификатор и контрольные характеристики исходных данных.
3. Клиент генерирует или получает криптографический ключ.
4. Данные шифруются на стороне клиента.
5. Зашифрованный объект разбивается на блоки.
6. Erasure Coding создаёт дополнительные фрагменты.
7. Фрагменты распределяются между выбранными узлами.
8. Система сохраняет манифест размещения.
9. Узлы подтверждают приём данных.
10. Система периодически проверяет состояние хранения.
11. При отказах выполняется восстановление избыточности или исходного объекта.
12. Пользователь может восстановить исходный файл при наличии достаточного количества корректных фрагментов и необходимых ключей.

Подтверждение приёма данных не является доказательством длительного хранения.

5.2. Encryption

Основной принцип: Plaintext must not leave the trusted client boundary.

Предлагается использовать проверенные криптографические библиотеки и стандартные алгоритмы аутентифицированного шифрования.

В качестве кандидата для шифрования данных рассматривается AES-256-GCM.

Требования: уникальный nonce для каждой операции шифрования в рамках одного ключа; проверка authentication tag; безопасная генерация ключей; отсутствие хранения открытых ключей шифрования в публичной DHT; отсутствие передачи секретных ключей узлам хранения; защита от повторного использования nonce; документированное управление жизненным циклом ключей.

Ключи должны оставаться под контролем владельца данных.

Потеря ключей может привести к невозможности восстановления исходного содержимого даже при физическом наличии всех фрагментов.

Управление резервным копированием и восстановлением ключей требует отдельной спецификации.

5.3. Chunking

Большие объекты могут разбиваться на независимые блоки.

Для каждого блока необходимо сохранять: Object ID; Chunk ID; порядковый номер; размер; криптографический hash; связь с исходным объектом.

Размер блока не фиксируется в этой версии документа.

Он должен определяться экспериментально с учётом сетевого трафика; количества операций; задержек; доступной памяти; стоимости восстановления; поведения мобильных узлов.

5.4. Erasure Coding

Для повышения устойчивости предлагается использовать Erasure Coding.

Схема задаётся двумя параметрами: K — количество исходных data shards; M — количество дополнительных parity shards.

Общее количество фрагментов: N = K + M.

Для восстановления требуется достаточное количество корректных фрагментов согласно используемому коду.

Candidate Profile: 10+20

Предварительная схема MVP: K = 10; M = 20; N = 30.

Это означает создание 30 фрагментов, из которых 10 являются информационными, а 20 — избыточными.

При корректной реализации подходящего Erasure Coding-кода восстановление возможно при наличии любых 10 корректных фрагментов из 30.

Важно: 10+20 — кандидат для испытания, а не подтверждённый стандарт; необходимо проверить совместимость кодирования и декодирования; необходимо проверить поведение при повреждённых фрагментах; необходимо проверить реальные затраты трафика и дискового пространства; необходимо проверить распределение фрагментов между независимыми узлами.

Количество фрагментов не равно количеству узлов.

Размещение нескольких фрагментов на одном физическом устройстве создаёт общий домен отказа.

Поэтому Placement Engine должен учитывать независимость узлов и инфраструктурные домены отказа.

6. Network Layer

6.1. Peer-to-Peer Communication

Узлы должны иметь возможность обнаруживать друг друга и обмениваться данными без обязательного центрального сервера хранения.

Архитектура предусматривает: обнаружение участников; установление соединений; обмен метаданными; передачу фрагментов; контроль целостности; обработку недоступности узлов.

Конкретный транспортный протокол требует отдельного технического решения.

6.2. Kademlia DHT

В качестве кандидата для распределённого обнаружения узлов и записей рассматривается Kademlia Distributed Hash Table.

Предполагаемые функции: распределённое хранение записей обнаружения; поиск узлов; маршрутизация запросов; поиск доступных участников; отсутствие единственной обязательной точки обнаружения.

DHT не является доверенным реестром.

Наличие записи в DHT не доказывает физическое существование узла; наличие данных; сохранность фрагмента; доступность узла; независимость узла от других участников.

DHT используется для обнаружения, а не для окончательной верификации.

6.3. Network Security

Сетевой слой должен учитывать: Sybil attacks; Eclipse attacks; replay attacks; routing manipulation; denial-of-service; подмену идентичности; вредоносные записи DHT; сговор участников.

Уровень защиты и конкретные механизмы противодействия должны быть определены в отдельной спецификации сетевой безопасности.

7. Placement and Replication

Placement Engine отвечает за выбор узлов, на которых размещаются фрагменты.

При выборе необходимо учитывать: доступную ёмкость; текущую загрузку; наблюдаемую доступность; сетевую близость; пропускную способность; независимость доменов отказа; географическое распределение, если оно доступно и допустимо; ограничения пользователя.

Система не должна размещать все критические фрагменты в одном домене отказа.

Replication и Erasure Coding являются разными механизмами.

Replication создаёт дополнительные копии данных.

Erasure Coding создаёт набор информационных и избыточных фрагментов.

Выбор между ними или их совместное применение должен определяться требованиями к надёжности; стоимости хранения; трафику; скорости восстановления; доступности.

Конкретная стратегия репликации в v0.1 остаётся открытым архитектурным параметром.

8. Integrity and Evidence

8.1. Cryptographic Integrity

Каждый фрагмент должен иметь проверяемый криптографический идентификатор.

Клиент должен иметь возможность обнаружить: изменение данных; повреждение; подмену; несоответствие манифесту.

Хеширование подтверждает соответствие проверяемых байтов ожидаемому значению, но не доказывает длительное хранение.

8.2. Distinct Proof Claims

Следующие утверждения должны оставаться раздельными.

Proof of Possession — свидетельство того, что узел в конкретный момент способен предъявить определённые данные или их часть.

Proof of Storage — криптографическое свидетельство, предназначенное для проверки хранения данных в заданной модели угроз. Конкретная схема и её гарантии должны быть определены отдельно.

Proof of Availability — свидетельство того, что узел или данные были доступны в определённом временном интервале согласно установленной методике проверки.

Proof of Bandwidth — измерительное свидетельство о передаче определённого объёма данных с наблюдаемыми характеристиками.

Эти доказательства не взаимозаменяемы.

Например: успешный ответ узла не доказывает длительное хранение; наличие hash не доказывает доступность; успешная передача файла не доказывает постоянную пропускную способность; Proof of Possession не автоматически становится Proof of Storage.

8.3. Evidence Interface

EVERYNODE должен предоставлять структурированные свидетельства для независимого анализа.

Предполагаемые поля: Evidence ID; Node ID; Object ID; Chunk ID; Challenge ID; тип проверяемого утверждения; время создания; параметры проверки; криптографические данные; результат локальной проверки; версия протокола; ссылка на исходные данные проверки.

Формат и обязательные поля будут определены в отдельном документе: "JAMP_EVERYNODE_INTEGRATION_CONTRACT_v0.1.md"

EVERYNODE не должен самостоятельно объявлять результаты своих внутренних проверок окончательным независимым вердиктом JAMP.

9. Availability and Recovery

Система должна учитывать, что узлы могут: отключаться; менять сетевое подключение; терять питание; удалять локальные данные; повреждать фрагменты; прекращать участие; становиться временно недоступными.

Recovery Engine должен:

1. обнаруживать недостаточную доступность фрагментов;
2. определять возможность восстановления;
3. находить доступные корректные фрагменты;
4. восстанавливать недостающую избыточность;
5. проверять целостность восстановленных фрагментов;
6. обновлять манифест размещения;
7. сохранять свидетельства операции.

Восстановление должно завершаться проверкой целостности результата.

Успешное завершение сетевой операции без проверки восстановленных данных не считается доказательством корректного восстановления.

10. Threat Model

Архитектура должна учитывать следующие угрозы.

Sybil Attack | Создание множества фиктивных идентичностей | Механизмы оценки независимости узлов
Collusion | Сговор нескольких участников | Независимые проверки и разделение доменов отказа
Data Tampering | Изменение фрагментов | Криптографическая проверка целостности
Data Deletion | Удаление сохранённых фрагментов | Проверка наличия и восстановление избыточности
False Availability | Ложное заявление о доступности | Независимые challenge-механизмы
Replay Attack | Повторное использование старых ответов | Свежие challenge и защита от повторов
DHT Manipulation | Манипуляция записями обнаружения | Проверка идентичности и независимая валидация
Bandwidth Abuse | Искажение результатов измерений | Контролируемые измерения передачи
Key Loss | Потеря ключа владельцем | Отдельная стратегия восстановления ключей
Resource Exhaustion | Исчерпание диска, памяти или сети | Лимиты и контроль ресурсов

Ни один отдельный механизм не считается достаточной защитой от всех перечисленных угроз.

11. Privacy and Data Ownership

Владелец данных должен сохранять контроль над: исходным содержимым; ключами шифрования; правами на восстановление; удалением данных; разрешением на использование ресурсов.

Узлы хранения не должны получать больше пользовательских данных, чем необходимо для выполнения их технической функции.

Метаданные также могут раскрывать чувствительную информацию.

Поэтому необходимо минимизировать: идентификаторы объектов в открытом виде; сведения о владельцах; историю операций; сетевые связи между участниками; информацию о содержимом и структуре файлов.

Конкретные требования к персональным данным и юридическим обязанностям определяются отдельно в "LEGAL_SCOPE.md".

12. Modular Expansion

Архитектура должна допускать последующее расширение инфраструктурными модулями.

Storage | Хранение данных
Bandwidth | Передача данных
Compute | Вычислительные ресурсы
Relay | Сетевое посредничество
Edge AI | Распределённые AI-вычисления

Эти модули не входят автоматически в MVP.

Каждый новый модуль должен иметь: отдельный контракт; модель ресурсов; модель угроз; проверяемые свидетельства; критерии приёмки; независимую оценку безопасности.

Добавление новых модулей не должно нарушать базовую архитектуру хранения.

13. Technology Selection Policy

v0.1 определяет архитектурные направления, но не фиксирует окончательный технологический стек.

Node Agent | Rust
Data Encryption | AES-256-GCM или другой проверенный AEAD
Erasure Coding | Проверенная реализация Reed-Solomon или эквивалент
Discovery | Kademlia DHT
Integrity | SHA-256 или другой утверждённый криптографический hash
Communication | Защищённый P2P-транспорт

Выбор конкретных библиотек, версий и протоколов требует отдельной оценки.

Критерии выбора: безопасность; зрелость реализации; поддержка платформ; производительность; воспроизводимость сборок; лицензирование; возможность независимого аудита; совместимость с будущими версиями протокола.

14. MVP Architectural Boundary

Первый технический MVP должен проверять базовую возможность распределённого хранения и восстановления данных.

Предварительная архитектурная модель: несколько независимых узлов; клиентское шифрование; разбиение данных; Erasure Coding; распределение фрагментов; отключение части узлов; восстановление исходного объекта; проверка целостности.

Конкретные размеры данных, количество узлов, профиль Erasure Coding и критерии успешности определяются документом: "EVERYNODE_MVP_ACCEPTANCE_CRITERIA_v0.1.md"

MVP не должен доказывать готовность публичной сети или промышленную надёжность.

15. Explicit Non-Goals

Следующие направления исключены из текущего технического фундамента: выпуск собственного токена; токеномика; инвестиционные предложения; гарантированные выплаты участникам; публичные обещания доходности; автоматическое вознаграждение за неподтверждённые ресурсы; промышленный SLA; утверждение о полной децентрализации без независимого аудита; утверждение о доказанной безопасности без тестирования; интеграция EVERYNODE как внутреннего модуля JAMP Core.

Экономическая модель и юридические границы рассматриваются отдельно.

16. Relationship with JAMP

JAMP является независимым Trust Layer.

EVERYNODE является Infrastructure Layer.

Границы ответственности:

EVERYNODE: выполняет хранение; распределяет данные; обнаруживает узлы; формирует технические свидетельства; выполняет восстановление.

JAMP: получает свидетельства; проверяет их происхождение и целостность; анализирует достаточность доказательств; выявляет противоречия; формирует независимый вердикт.

JAMP не должен принимать внутренний статус EVERYNODE как достаточное доказательство.

EVERYNODE не должен иметь возможности самостоятельно назначать себе статус VERIFIED в JAMP.

При отсутствии достаточных доказательств JAMP должен применять Fail-Closed.

Взаимодействие будет определено отдельным интеграционным контрактом.
