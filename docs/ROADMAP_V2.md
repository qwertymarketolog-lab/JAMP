# JAMP — Trust Layer Roadmap v2.0

**Девиз:** *JAMP не продаёт уверенность модели. JAMP продаёт проверяемость утверждений.*  
**Дата фиксации:** 26.10.2026

> **Evidence boundary (обязателен для читателя).** Этот документ фиксирует целевую продуктовую дорожную карту и ранее заявленные результаты, но не повышает их доказательный статус сам по себе. На текущем `main` файл `STATUS.md` описывает исследовательские результаты Track A / P18.4 / P24-B и прямо перечисляет ограничения проекта; он не подтверждает весь описанный ниже Trust Layer runtime. Поэтому пункты без привязанных к ним проверяемых Run → Job → artifact / исходных контрактов не следует считать подтверждёнными только на основании этого roadmap. Статусы ниже намеренно разделяют исторические свидетельства, неподтверждённые заявления и будущие работы.

## Часть 1: Состояние и границы доказательств

Цель проекта — инфраструктура доказательств: каждое утверждение должно быть связано с проверяемым происхождением, результатом проверки и явным уровнем уверенности. Успешное выполнение кода само по себе не доказывает исследовательскую гипотезу, качество модели или production readiness.

### Stage 1: MVP (Telegram Integration) — NOT VERIFIED IN CURRENT MAIN
Заявленная цель: транспорт Telegram, обработка входящих сообщений и отправка ответов. В текущем `STATUS.md` нет достаточной цепочки доказательств, чтобы объявить этот этап подтверждённым состоянием текущего `main`.

### Stage 2: E2 (Fail-Closed Verdict) — NOT VERIFIED IN CURRENT MAIN
Заявленная цель: независимая проверка генерации через OpenRouter API и отказ, если обязательные доказательства отсутствуют. Для статуса VERIFIED нужны конкретные контракт, тесты и терминальные CI evidence; описание roadmap их не заменяет.

### Stage 3: Data Experiments (Financial & Stock) — HISTORICAL EVIDENCE; SCOPE LIMITED
В истории проекта был зафиксирован Financial Audit workflow на commit `733342bbd572c1f740080f4f68139f01b66c1c42`: Run `40226538958`, Job `121268992609`, artifact `12611043936`. Этот результат относится к тому commit и его конфигурации. Он не доказывает текущую конфигурацию `main`, универсальную точность или независимую проверку всех финансовых/биржевых сценариев. Актуальность после изменений конфигурации проверяется отдельным запуском.

### Stage 4: MCP Guard — NOT VERIFIED IN CURRENT MAIN
Заявленная цель: блокировать инструменты с `destructiveHint: true` без подтверждения. Не объявлять механизм действующим контролем без исходного кода, тестов и evidence, подтверждающих этот контракт.

### Stage 5: Signed Verdict (JampVerdict) — NOT VERIFIED IN CURRENT MAIN
Заявленная цель: HMAC-SHA256 для сертификатов качества. Криптографическая подпись коммита не равнозначна подписи JampVerdict. До подтверждения реализации, формата подписи, верификации и тестов сертификат качества нельзя называть криптографически подтверждённым.

### Stage 6: Qualification Engine (E3) — HISTORICAL, BOUNDED MVP EVIDENCE
Для Financial Audit на commit `733342bbd572c1f740080f4f68139f01b66c1c42` был зафиксирован результат 5/5, score 1.0 для GLM в наборе `synthetic_financial_extraction_v1`. Это ограниченное свидетельство на пяти тестовых случаях, а не независимый широкий benchmark и не доказательство production readiness. Текущую квалификацию необходимо связывать с точной версией датасета, конфигурацией маршрутизации, реальным результатом тестов и артефактом.

### Frozen Core — INVARIANT
Защищённый файл: `src/jamp/run.py`. Ожидаемый blob SHA: `0fee0e1c5c1a1548361965ac51eacdeba62bfe8a`. Для каждого изменения проверять blob напрямую и фиксировать `Δ = 0`. Любое изменение допускается только после отдельного архитектурного решения (Core Unlock). На проверенном чтении `main` blob совпал с ожидаемым SHA; это подтверждает только идентичность файла в момент чтения, а не неизменность на всём историческом пути.

## Часть 2: Следующий рубеж — B2B Productization

**Цель:** превратить доказательные механизмы в интегрируемый продукт. Все этапы ниже — план, а не заявление о готовой реализации.

### Stage 7: Trust Layer API (B2B Endpoint) — PLANNED
Спроектировать и реализовать выделенный endpoint `/v1/trust-layer/execute`, который связывает исполнение, проверку доказательств, квалификацию и формирование вердикта. Предусмотреть `/v1/verify-verdict` для независимой проверки результата. До объявления этапа выполненным требуются API-контракт, тесты отказов, интеграционные тесты и терминальные CI evidence.

### Stage 8: Production MCP & Real Integrations — PLANNED
Подключать реальные инструменты только через явные границы разрешений и подтверждения. Проверять результат независимо от сообщения инструмента: например, если инструмент утверждает, что файл сохранён, повторно прочитать файл и сверить хеш. Отдельно фиксировать ограничения каждого интеграционного адаптера.

### Stage 9: The First B2B Pilot (Financial/Data Audit) — PLANNED
Выбрать реальный сценарий с клиентом или независимым владельцем данных. Измерить базовую линию и результат: число обнаруженных ошибок/подмен, ложные срабатывания, время проверки и экономический эффект. Не заявлять экономию без измерений и согласованной методики.

### Stage 10: Scaling & Commercialization — PLANNED
- Расширить квалификационные бенчмарки воспроизводимыми наборами тестов и независимой разметкой.
- Рассмотреть PostgreSQL для истории вердиктов вместо файлов JSONL после определения схемы, миграции и требований к аудиту.
- Разработать UI-дашборд для просмотра вердиктов, происхождения данных, конфликтов и отказов.
- Определить модель доступа, хранение данных, сроки удержания, эксплуатационные SLO и границы ответственности.

## Принципиальные ограничения (Constraints)

1. **Fail-Closed:** если обязательных доказательств нет, положительный вердикт не выдаётся. HTTP 502 допустим только там, где это предусмотрено и проверено контрактом API; не считать код ответа глобально доказанным без тестов.
2. **No Synthetic PASS:** квалификация выводится из фактических результатов тестов. Запрещены хардкод статуса/score и повышение UNKNOWN/INCONCLUSIVE до VERIFIED.
3. **Прозрачность маршрутизации:** Crosswalk и выбранная фактическая модель фиксируются в артефактах. Запрошенный model ID и фактически использованный provider model ID — разные поля; их несовпадение должно быть объяснимо и видимо.
4. **Frozen Core:** изменение `src/jamp/run.py` требует отдельного архитектурного решения (Core Unlock).
5. **Сохранение конфликтов:** противоречивые источники фиксируются как AMBIGUOUS; конфликт нельзя сглаживать выбором удобного значения.
6. **CI-доказательства:** для каждого заявления о CI указывать SHA, Workflow, Run ID, Job ID, Conclusion и Artifact. Отсутствующие jobs или артефакты не означают PASS.
7. **Production readiness:** успешный CI, ограниченный benchmark или исторический E2E по отдельности не доказывают готовность к production.

## Критерий перехода этапа

Этап меняет статус только при наличии проверяемого Definition of Done и связанной цепочки доказательств. План, документация, успешный HTTP-ответ и единичный тестовый пример не заменяют независимую проверку результата.
